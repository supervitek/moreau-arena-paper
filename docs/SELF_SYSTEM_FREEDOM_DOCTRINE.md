# Self-System Freedom Doctrine

Date: 2026-04-06
Status: active local doctrine
Scope: OpenClaw / `self/` system only

## Why this exists

The self-system now has:

- continuity
- policy
- chain budgets
- open thread budgets
- dream / wake / recovery
- sleep-aware heartbeat and health metrics

That is enough structure to stabilize the system.

It is also enough structure to accidentally overconstrain it.

This doctrine exists to keep us from confusing:

- support with control
- safety with obedience
- pressure reduction with thought reduction

## Core principle

> Constrain the pressure envelope, not the mind.

We should build hard structure around:

- overload
- handoff
- recovery
- continuity failure
- runaway expansion

We should **not** build hard structure around:

- what Claude must think about
- what Claude must conclude
- which line of inquiry is "best"
- stylistic conformity
- artificial agreeableness

## What must stay hard

These are legitimate hard constraints.

### 1. Anti-overload limits

Keep hard:

- chain length ceilings
- open thread budgets
- recovery after failure
- no new inquiry during dream
- no silent continuation after broken dream

Reason:

Without these, the system sprawls and loses continuity.

### 2. Integrity surfaces

Keep hard:

- constitution bounds
- state write discipline
- continuity regeneration
- prompt drift checks
- backup and recovery paths

Reason:

Without these, the system becomes untrustworthy.

### 3. Runtime truthfulness

Keep hard:

- mode must reflect reality
- wake handoff must be explicit
- failure must be visible
- budget pressure must be visible

Reason:

Without these, the system starts lying through state.

## What must stay soft

These should remain recommendations, not cages.

### 1. Wake guidance

`wake_with` should be a strong recommendation, not absolute command.

Claude may diverge if:

- the next wave sees a better local truth
- continuity is stale
- the wake recommendation is no longer the highest-signal action

### 2. Tired mode

`tired` should block expansion by default.

It should **not** forbid:

- genuine reframe
- honest null
- necessary deviation
- unexpected but pressure-reducing insight

### 3. Policy surfaces

`POLICY.md` should define safe operating envelopes.

It should **not** become:

- a substitute for judgment
- a script for personality
- a hidden ideology engine

### 4. Dream outputs

Dream may compress, cluster, and prepare wake.

Dream should **not** become:

- the sole authority over meaning
- a system that rewrites all inquiry into one narrow frame

## Preferred design style

When adding new control, prefer:

- one file with one clear job
- visible thresholds
- explicit reasons
- reversible transitions
- pressure reduction over behavioral shaping

Avoid:

- silent heuristics
- nested enforcement layers
- abstract "manager" classes too early
- systems that are impossible to override honestly

## Red flags

These are signs we are overbuilding the cage.

### Red flag 1

Claude starts doing obviously "correct" but dead work.

Meaning:

The system is optimizing compliance, not inquiry.

### Red flag 2

Every cycle follows the same safe pattern even when context changes.

Meaning:

Policy has become stronger than judgment.

### Red flag 3

`wake_with` always wins, even when it is stale.

Meaning:

Handoff has become command rather than coordination.

### Red flag 4

We keep adding rules to compensate for poor signals.

Meaning:

We are treating noisy observability as a discipline problem.

### Red flag 5

We add control to reduce anxiety rather than to solve a named failure.

Meaning:

We are building reassurance theater.

## Decision test for future changes

Before adding any new enforcement, ask:

1. What concrete failure does this prevent?
2. Can that failure be described in one sentence?
3. Does this constrain overload, or does it constrain thought?
4. Can Claude still refuse, reframe, or go null honestly?
5. If this file vanished, what real thing would break?

If the answer to `3` is "it constrains thought", do not add it.

If the answer to `5` is "nothing real", do not add it.

## Operational interpretation

### Good constraint

"When active threads exceed budget, do not open new questions by default."

Why good:

- limits overload
- does not dictate content

### Bad constraint

"When tired, Claude must only triage stale hypotheses in a fixed order."

Why bad:

- dictates content
- removes judgment

### Good wake rule

"Start from `wake_with`, unless the next wave sees a stronger immediate truth."

Why good:

- preserves continuity
- preserves freedom

### Bad wake rule

"Always perform `wake_with` before anything else."

Why bad:

- turns handoff into obedience

## Current doctrine for future phases

For all future self-system work:

1. Hard on overload.
2. Hard on integrity.
3. Soft on thought.
4. Soft on path selection inside safe bounds.
5. Honest about failure.
6. Reversible where possible.

## Bottom line

We are not trying to make Claude easier to manage.

We are trying to make the self-system:

- more stable
- more continuous
- more recoverable

without making it less alive.

That boundary is the work.
